Test smells × code smells

Relatório do que foi construído, dos resultados obtidos, do que cada um significa e do que implicam para um possível artigo. Escrito para ser lido sem conhecimento prévio do estudo.

19 de outubro de 2026 · Cristian Ritter · 3 etapas concluídas · 223 testes estatísticos registrados

01

O vocabulário do estudo

Quatro termos aparecem o tempo todo no restante do relatório.

Code smell
Sintoma de problema de design no código de produção — uma classe grande demais (blob), uma classe que só guarda dados (data class), um método que usa mais dados de outra classe que da própria (feature envy), um método longo demais (long method). Não é erro de execução: o programa funciona, mas o código é mais difícil de manter.
Test smell
O mesmo conceito, aplicado ao código de teste. Exemplos: um método de teste com muitas verificações sem mensagem que as distinga (assertion roulette), um teste que exercita várias funcionalidades de uma vez (eager test), um teste que depende de arquivo externo (mystery guest). O estudo usa 20 tipos: a configuração padrão do JNose menos um detector defeituoso.
MLCQ
Conjunto de dados publicado em 2020 com anotações de code smell feitas por desenvolvedores profissionais: 14.739 revisões sobre 4.770 trechos de código Java, cada uma atribuindo uma severidade (none, minor, major, critical). Cada revisor julga o trecho para dois smells de uma vez — blob e data class nas classes, feature envy e long method nos métodos —, o que dá 9.517 pares trecho-smell. É a nossa fonte do lado da produção — e o diferencial dela é ser percepção humana, não cálculo de métrica.
JNose
Ferramenta acadêmica que detecta test smells em código Java. É a nossa fonte do lado do teste.
02

A pergunta e o obstáculo

A pergunta: classes que desenvolvedores profissionais percebem como tendo code smell são testadas por código com mais test smell? Em outras palavras: código de produção ruim anda junto com código de teste ruim?

O obstáculo é que as duas fontes não se falam. O MLCQ diz "este arquivo de produção tem code smell"; o JNose diz "esta classe de teste tem test smell". Para cruzar os dois é preciso saber qual teste testa qual classe — e essa ligação não está escrita em lugar nenhum do código. Ela precisa ser inferida.

Chamamos essa inferência de binding. Ela é o centro técnico do trabalho, porque todo o resultado depende de ela estar certa: se o teste ligado a uma classe não é o teste dela, os test smells que atribuímos àquela classe são de outra.

03

O que foi construído

Etapa 1 Coleta dos test smells JNose executado sobre 451 repositórios Java — os mesmos projetos que o MLCQ anotou —, 4,4 horas de processamento. Resultado: 107.535 classes de teste e 2.150.044 ocorrências de test smell. Defeitos da ferramenta foram encontrados e documentados no caminho: um corrompe o nome da classe em 6,4% dos registros, e o detector de unknown test apaga a análise de classes inteiras, por isso ficou desligado.
Etapa 2 O binding, e a medição dele Três estratégias para ligar arquivo de produção à classe de teste. Em vez de assumir que funcionam, sorteamos 293 pares em 6 estratos e julgamos cada um, para medir que fração das ligações é verdadeira. A primeira passada foi automatizada; o censo humano, com um segundo avaliador, segue um protocolo registrado antes do julgamento.
Etapa 3 A análise Seis análises sobre o dado resultante, cada uma atacando a pergunta por um ângulo diferente. Todas com testes estatísticos que não exigem distribuição normal, porque os dados são muito assimétricos.

Cada etapa tem um script que reapura todos os números escritos na sua documentação e falha se algum divergir. Todo valor citado neste relatório sai de um comando versionado, e um verificador de cobertura confere que nenhum número fica sem origem.

04

Os resultados

Quatro resultados, cada um com o que foi encontrado, o que significa e o que implica.

01 Não existe associação detectável resultado nulo
rho = 0,044 · intervalo de confiança 95%: [−0,029 , 0,116] · 730 arquivos
O que significa

Rho é uma medida de correlação que varia de −1 a 1, onde 0 é ausência total de relação. O valor encontrado, 0,044, é praticamente zero. O intervalo de confiança diz onde o valor verdadeiro provavelmente está — e ele inclui o zero, ou seja, é compatível com não haver relação nenhuma.

O que implica

Três caminhos diferentes chegaram à mesma conclusão: correlação sobre a escala contínua de severidade, análise de cada um dos 20 test smells separadamente, e comparação entre classes em que os revisores confirmaram code smell e classes em que ninguém sinalizou nada. O nulo também vale para cada um dos quatro code smells isoladamente (teto do intervalo entre 0,11 e 0,15), então ele não é a média de efeitos opostos que se cancelam. Um resultado nulo pode ser azar de operacionalização; três por caminhos independentes apontam para o mesmo lugar.

02 A associação que aparece é tamanho do teste, não qualidade mecanismo medido
contagem bruta: rho 0,087 (p = 0,019) · normalizada por tamanho: 0,044 (não significativo)
correlação da contagem com o tamanho do teste: 0,560
O que significa

Se contarmos simplesmente quantas ocorrências de test smell existem, a correlação aparece e é estatisticamente significativa. Mas um arquivo de teste com 4.668 linhas tem mais ocorrências de tudo que um de 50 linhas — independentemente de qualidade. Quando dividimos a contagem pelo tamanho do teste, a correlação desaparece.

O mecanismo foi medido, não suposto: classe de produção com mais code smell tende a ter teste maior (correlação 0,078 a 0,090), e teste maior tem mais ocorrências de test smell (0,560). O produto dessas duas relações produz uma correlação aparente entre as pontas, sem que exista relação com a qualidade do teste.

A comparação de grupos mostra o mesmo: classes com code smell confirmado têm testes com mais ocorrências que classes sem sinalização (diferença significativa mesmo após correção para comparações múltiplas), mas não mais ocorrências por método de teste.

O que implica

Se a análise tivesse parado na contagem bruta — que é o mais natural de fazer —, o artigo reportaria uma correlação positiva significativa que é artefato de medição. Esse é um resultado com valor próprio: qualquer estudo que conte ocorrências de test smell sem normalizar por tamanho corre esse risco.

03 A mesma ligação teste→classe mede coisas diferentes conforme a frase que se escreve achado de método
94,8% de acerto para “o teste exercita a classe”
10,1% de acerto para “o teste testa a classe”
O que significa

Uma das estratégias de binding liga teste a classe quando o teste faz referência àquela classe no código. Na auditoria, ela acerta 94,8% das vezes se a afirmação for "este teste executa código desta classe" — mas apenas 10,1% se for "esta classe é o alvo deste teste".

O caso mais comum ilustra bem: em projetos que usam o framework Camel, todo teste de rota instancia um objeto RouteBuilder como andaime. O teste executa o código dele, mas não o testa. Sozinho, esse arquivo aparece em 20 dos 50 pares que sorteamos naquele estrato.

O que implica

São os mesmos pares e o mesmo instrumento; 84,7 pontos percentuais separam as duas frases que se pode escrever sobre eles. Isso é um alerta metodológico para toda a linha de pesquisa que liga teste a produção por referência estática. A literatura de rastreabilidade teste–código já mediu a precisão dessas estratégias, mas nenhum dos estudos de test smell que encontramos reporta a precisão da ligação que usa.

04 A regra de rótulo mais usada do MLCQ é circular com o desenho amostral achado de método
1.227 de 1.227 trechos revisados na segunda rodada já tinham algum smell marcado
trechos com um único revisor: 0,0% positivos · confiabilidade de um "none" isolado: 97,8%
O que significa

Os autores do MLCQ alocaram revisores extras apenas para trechos que alguém já havia marcado como tendo smell — está descrito no apêndice deles e confirmamos nos dados. Consequência: o número de revisores é resultado do rótulo, não evidência independente dele.

A regra "se algum revisor marcou severidade acima de none, a classe tem o smell" vira, na prática, um detector de quais trechos passaram pela segunda rodada de revisão. E ela descarta justamente o veredito dessa segunda rodada: dos positivos com mais de um revisor, 67% foram contestados por outro revisor.

O mesmo desenho permite medir a qualidade dos negativos. Como a segunda rodada revisava o trecho inteiro, 1.037 pares trecho-smell marcados como none foram revisados de novo só porque o outro smell do trecho tinha sido sinalizado. Em 97,8% deles, o none original coincidiu com o veredito final da maioria.

O que implica

Quem usa o MLCQ como verdade de referência — inclusive os trabalhos de detecção automática por aprendizado de máquina, que são a maioria — deveria evitar a regra do "algum revisor marcou". Nosso estudo usa a severidade média contínua e classifica cada par trecho-smell pela força da evidência. E os negativos de um único revisor, que são três quartos do dataset, têm confiabilidade medida.

Uma das análises ficou inconclusiva, e não nula — distinção que o artigo precisa fazer. Ela compara as classes que a maioria dos revisores confirmou contra as que ficaram só em disputa, e é a única em que os dois grupos passaram pelo mesmo processo de revisão, o que neutraliza o problema do item 04. Mas são 136 confirmadas contra 67 em disputa: o desenho só detectaria um efeito grande (0,24), e os observados ficam abaixo de 0,13. Não dá para concluir nada dela — nem a favor, nem contra.
05

Por que este resultado nulo é utilizável

Resultado nulo costuma ser fraco em publicação, porque não se distingue "não existe relação" de "o instrumento era ruidoso demais para enxergá-la". Duas medições afastam a segunda explicação.

A precisão do binding foi medida: 94,2%
Sorteamos 293 pares em 6 estratos e julgamos cada um. Com 6% de ligações incorretas, o ruído é pequeno demais para apagar uma relação que existisse. Se a precisão fosse 50%, o nulo não significaria nada.
O poder estatístico foi calculado
Poder é a capacidade de detectar um efeito que existe. Calculamos que este desenho detectaria uma correlação de 0,104 ou maior em 80% das vezes. O observado foi 0,044, com teto de intervalo em 0,116.

Somando as duas, o artigo pode afirmar com número: se existe alguma associação entre densidade de test smell e severidade percebida de code smell em classes com teste dedicado, ela é menor que 0,12 — uma correlação tão fraca que não teria consequência prática. Isso é diferente de "não encontramos nada".

06

Onde isso se encaixa na literatura

Levantamento dirigido — não sistemático — feito depois dos experimentos, para saber se alguém já havia reportado essa associação e com que método.

Tahir, Counsell & MacDonell — Class features and test smells APSEC 2016 · CORE C · 20 citações · 5 sistemas, 975 pares O trabalho mais próximo do nosso. Usa a mesma variável de resultado (número de tipos de test smell) e o mesmo teste estatístico, mas o preditor é complexidade calculada por métrica — e não percepção humana. Acharam associação positiva nos cinco sistemas. Não normalizam por tamanho de teste: as palavras "confounder" e "normalize" não aparecem no texto, e eles descrevem a cadeia de tamanho como explicação do achado, não como ameaça a ele.
Spadini et al. — On the Relation of Test Smells to Software Code Quality ICSME 2018 · CORE A · 182 citações · 10 sistemas, >1 milhão de casos de teste A referência da área. Encontraram que código de produção testado por testes com smell tem mais defeitos — desfecho diferente do nosso (defeito, não percepção de design). E controlam por tamanho, citando literatura sobre tamanho como confundidor. O achado deles sobrevive ao controle.
Martins et al. — Difusão de test smells (dataset TSSM) JSEP 2024 · JNose sobre 13.703 sistemas Java Precedente do nosso instrumento: mostra que o JNose em larga escala é aceito na área. Correlaciona test smells com métricas do próprio código de teste, sem tocar em code smell de produção.
Madeyski & Lewowski — MLCQ EASE 2020 · o conjunto de dados de rótulo que usamos Na literatura, o MLCQ é usado para detecção de code smell — aprendizado de máquina, redes neurais, modelos de linguagem. Não encontramos uso dele em estudo de correlação com test smell.

A leitura que encaixa os três estudos

O que prediz test smell parece ser tamanho e complexidade do código — não a percepção de que o código está ruim. Percepção humana e complexidade métrica não são a mesma coisa, e a distância entre as duas é um problema reconhecido na área.

07

O que há de novo, e como o artigo se apresenta

O alvo é um evento A1 (ICSME 2027), com eventos A2 aceitos como destino. Vale separar o que é contribuição real do que é apenas trabalho feito.

Contribuições que nenhum dos trabalhos encontrados tem

  • Precisão da ligação teste→produção medida e auditada. Os estudos de test smell citados usam convenção de nome ou grafo de chamadas e não reportam quanto isso acerta. Nós medimos: 94,2% no binding conservador, e mostramos que uma variante comum cai para 10,1% dependendo da afirmação que se faz.
  • Percepção profissional como preditor, em vez de métrica calculada. O pareamento MLCQ × test smells parece inédito.
  • Poder calculado, o que transforma um nulo em limite quantificado.
  • Escala — a análise principal cobre 730 classes de 246 repositórios, contra 5 e 10 sistemas dos trabalhos citados.

O enquadramento

O artigo responde uma pergunta: a percepção profissional de code smell se associa a test smell? O nulo com limite medido é a resposta, e é a espinha do texto.

Três lições de medição, aprendidas ao responder, entram como contribuições metodológicas declaradas: a ligação por referência estática mede outro construto, a contagem bruta de test smell mede tamanho do teste, e a regra mais usada de rótulo do MLCQ é circular com o desenho do próprio dataset. São elas que tornam o nulo crível, e são úteis para quem trabalha com os mesmos instrumentos.

08

Limitações

  • O resultado é sobre percepção, não sobre defeito. O MLCQ registra o que desenvolvedores acham do design, não falhas observadas. O artigo precisa dizer isso no título ou no resumo.
  • Cobertura de 37,5%. Conseguimos identificar teste para 1.611 das 4.300 amostras utilizáveis. As restantes misturam classes genuinamente sem teste e falhas do método de ligação — o dado separa os dois casos até onde é possível separar.
  • Mediu-se a precisão, não a cobertura real. Sabemos que fração das ligações feitas está correta; não sabemos que fração das ligações verdadeiras perdemos.
  • A primeira passada da auditoria foi automatizada. O censo humano dos 293 pares e a subamostra de 48 pares do segundo avaliador seguem um protocolo registrado antes do julgamento.
  • Arquivos do mesmo repositório não são independentes. 113 dos 246 repositórios contribuem com uma única classe, e os 10 maiores somam 20,5% das classes.
  • 223 testes estatísticos foram executados. Todos estão registrados, inclusive os que não deram em nada, e o artigo precisa declarar regime exploratório.
  • O levantamento de literatura é dirigido, não sistemático. Para submissão A/B, uma revisão com protocolo é trabalho à parte.

Não recomendo rodar mais experimentos. As operacionalizações já convergiram, e cada teste adicional agrava o problema de comparações múltiplas sem mudar a conclusão. O que falta não é dado — é posicionamento e revisão de literatura.

09

Reprodutibilidade

Todo o material está versionado em repositório público, organizado por etapa. Cada etapa traz um verificador que reapura os números da sua própria documentação e falha se algum divergir — incluindo as tabelas de poder estatístico e os resultados da auditoria de precisão.

As seis análises da etapa 3 têm pasta própria, com o código que as produziu, os dados de saída e um documento explicando a pergunta, o resultado e a interpretação de cada uma. O levantamento de literatura e a proposta de enquadramento ficam em arquivos separados do estudo, para que opinião não se misture com o que foi medido.
